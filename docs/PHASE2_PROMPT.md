## 1. 本阶段优先级与核心目标

- **P0-A：修复右侧待办拖入日历**：任何位于右侧待办区域、符合条件的任务都能拖入日/周时间轴，形成关联时间块，不能产生重复任务。
- **P0-B：解决日历重叠难以阅读**：长时间日程与短日程重叠时，不能相互遮挡或被压到标题逐字换行；实现“普通安排并列 + 可选背景安排分层”的双模式。
- **P1：重复日程**：支持固定课程、每周健身、日常事务，支持单次例外。
- **P1：时间轴与清单自定义**：时间粒度、显示范围、周起始日、视觉密度、显示筛选。
- **P2：子任务、标签、搜索及基础撤销**：在 P0、P1 稳定的前提下完成。

所有功能必须继续兼容纯静态网站、IndexedDB 和未来 GitHub Pages 部署。本阶段**不做 GitHub PAT、OAuth、远端同步、Cloudflare Worker 或多设备冲突合并**。

## 2. P0-A：右侧待办直接拖入日历

### 用户期待的行为

用户在右侧待办栏创建“完成实验报告”，用鼠标按住任务卡的拖拽手柄，拖到周三 19:00 后：

- 日历立即显示 19:00—20:00 的任务时间块（默认长度建议 60 分钟，支持后续在设置中调整）。
- 原任务仍然保留在右侧清单内，标题、状态、清单 ID、截止日期不变。
- 再次拖动同一个任务到周四 20:00，会得到**同一 Task 对应两条 ScheduleBlock**，而不是两个 Task。
- 日历中的块可继续移动/拉伸；点击它打开原任务及其安排详情。
- 数据写入 IndexedDB 成功才认定操作成功；写入失败需要撤销临时日历展示并提示。

### 实现要求

1. 优先调查并修复原有外部拖动逻辑，评估 FullCalendar 6 的 `@fullcalendar/interaction`、`Draggable`、`droppable`、`drop` 或 `eventReceive`；尽量采用一种明确的接入方式，避免一次拖动触发两次写入。若选择 `eventData.create = false`，须自行通过 `drop` 创建唯一正确的关联块。
2. 右侧任务卡使用明确的拖拽手柄，拖拽不影响勾选完成、文字编辑、点击查看详情、列表滚动；任务列表其他可复用展示区域如需支持拖入，也应复用同一逻辑。
3. 拖动期间显示合理的时间预览、放置反馈。允许拖到已有安排所在时段（显示冲突但不阻止）；不允许非法日期或无效时长。
4. 支持右侧面板动态筛选、重新渲染、切换清单、展开/折叠后仍能正确初始化和清理拖拽监听，不出现事件重复订阅或内存泄漏。
5. 支持日视图、周视图，其他视图的交互有明确规则；移动端/触摸设备如果双面板不能同时可见，保留通过表单“安排时间”完成相同功能，不强制依赖触摸拖拽。
6. 任务截止时间不等于执行时间，拖拽不会更改 dueDate、完成状态或删除原任务。

## 3. P0-B：重叠日程并列 + 背景分层

### 现有问题

用户已遇到：一个 **08:00—23:00** 的长日程和 **08:30—09:45** 的短日程相交，长块占据视觉焦点，短块被挤在角落，中文标题发生逐字换行，难以阅读。课程表与上课期间的个人安排叠加时尤其明显。

### 方案一：普通事件“并列”显示（默认）

1. 日/周 TimeGrid 中普通前景事件重叠时，必须相互错开并列展示，**不允许一个块覆盖另一个块的文字/点击区域**。先验证 `slotEventOverlap: false` 在现有 FullCalendar 6 的实际行为，不要假设这个开关能解决所有极窄列问题。
2. 优化事件卡片排版：时间优先保持清晰；标题在空间不足时最多合理截断/省略，不要每个汉字都单独占一行；完整标题和时间通过 hover、点击详情或可访问的提示得到。
3. 处理三条及以上同时重叠、窄屏和一个超长块覆盖整日的情况。可采用紧凑卡片、可展开更多事件、日视图提示、详情列表等渐进方案；**不允许用横向溢出破坏整个页面布局，也不能悄悄隐藏事件而无入口**。
4. 不允许为了视觉“错开”而偷偷更改真实开始/结束时间；并列只是显示策略，不改变业务数据。

### 方案二：可选“背景安排”分层

面向“上课期间还想安排某项任务”“一天内有长时间的课程/值班/研究区间”等场景。

1. 普通独立日程增加可选**显示层级**或“日历呈现方式”：
   - `normal`：普通前景安排，参与并列布局；
   - `background`：背景/上下文安排，在时间轴淡色高亮显示，**不占用普通前景时间块的并列宽度**。
2. 例如创建“理论力学 08:00—10:00”，将其标记为“背景安排”；同时间段安排“课堂笔记 08:30—09:15”时，前者作为浅色时间范围提示，后者清晰显示在上层。
3. 必须能识别背景安排的名称、时间、颜色，并有稳定可靠的**查看/编辑/删除入口**（例如日历旁的背景安排列表/详情面板）。FullCalendar 的背景事件不支持与普通事件一样原生拖动/拉伸，不能把背景模式做成无法编辑的死数据。
4. 背景安排不意味着任务真正从属于该课程，**Phase 2 不强行引入复杂的父子时间块实体引用**。它首先是一种显示层级，避免与真正的父子任务模型混淆。保留后续扩展空间即可。
5. 背景安排与普通日程可使用不同样式；用户可以在详情中切换 normal/background，设置持久化，升级旧数据默认 normal。
6. 单个时间段是否被占用不能因背景化而被错误判定为“没有事件”；如果有冲突提示，应根据实际时间范围而不是视觉宽度计算。
7. 保持颜色对比度与可访问性，浅色和深色主题均须测试。

### 两种模式的边界

- 并列用于两个独立事项确实同时发生。
- 背景用于课程、值班、时间范围、上下文计划之上叠加具体任务。
- 可以设置全局默认普通并列模式；每个独立日程可选择背景显示。不要因此额外引入需要付费的 FullCalendar Resource Timeline。

## 4. P1：重复日程（优先课程表）

实现可长期复用的重复独立日程：

1. 创建每天、每周、指定星期几、每 N 周、每月重复的日程；支持开始日期、结束条件（日期/次数或无限，具体以可靠实现为准）。
2. 使用明确的“重复规则 + 必要的例外记录”，**不要为了每周课程把几年内每一次都复制成一条独立 ScheduleBlock**。
3. 例如“每周一 08:00—09:35 理论力学”，跨周、跨月显示正确，时区变化时应符合当地墙上时间的重复语义（固定本地时刻与单次事件 UTC 存储不同）。保留 IANA 时区并明确解释。
4. 修改、删除重复日程时至少提供：“仅本次”“整个系列”；仅本次的修改需成为例外、仅本次删除需成为排除项，不破坏其他周。
5. 普通单次事件、任务关联时间块的数据语义保持不变；可以先仅支持 **event 类型**重复，重复任务执行块及重复生成任务不属于强制范围。
6. 课程也可设为背景层级，重复实例应正确继承背景显示，同时可处理单次例外。
7. 可选择免费 RRule 方案或自行实现小范围规则；以支持规则、时区、例外、序列化、测试为原则，不为增加依赖而增加依赖。

## 5. P1：时间轴、清单和视图设置

1. 时间粒度：15 / 30 / 60 分钟；保留默认合理值。
2. 可见时间段：例如 07:00—23:00；允许用户修改并在周/日视图生效。不要以此裁剪、删除实际数据；范围外任务须有明显查看途径。
3. 周起始日：周一 / 周日；设置持久化。
4. 页面密度：紧凑 / 舒适，重叠事件排版与可读性随设置合理变化。
5. 清单筛选与显示：允许指定哪些清单的任务安排出现在日历，沿用 Phase 1 的清单显隐逻辑；背景安排单独可筛选。
6. 尽量沿用现有三栏和移动端抽屉布局，右侧任务拖拽入口必须清晰可见；如不支持拖拽，则有明显的表单安排入口。
7. 第一阶段已有清单颜色、排序、归档、主题等能力不得回退。

## 6. P2：任务功能增强

在以上 P0/P1 完成且测试稳定后实现：

- **子任务**：任务下可建立和勾选子任务，支持稳定顺序；父任务完成规则明确（可允许父任务手动完成，不要暗中删除子任务）。子任务不自动成为日历事件。
- **标签**：用户可创建/重命名/调整颜色/删除标签，任务可关联多个标签；标签与清单是不同维度。
- **搜索**：跨清单搜索任务标题和描述；支持按状态、清单、标签及截止日期筛选，清楚标明是否包含归档项目。
- **撤销**：至少支持误删任务、删除时间块后的短时间撤销，并通过事务确保恢复后引用正确；明确撤销边界，不能因墓碑或历史记录留下虚假同步状态。

如果 P2 影响 P0/P1 稳定性，可以拆成清晰的小提交，但不得声称未实现的功能已完成。

## 7. 数据兼容、迁移与安全（强制）

1. **最重要：不能丢失用户 Phase 1 已经创建的清单、任务、日程、主题设置和 JSON 备份。** 用户当前本地 IndexedDB 可能已有真实数据。
2. 如果需要改变数据结构，应采用 Dexie version(2) 等正式升级路径，并保留对 schemaVersion=1 JSON 导入格式的兼容或提供明确可测试的安全迁移流程。
3. 迁移必须可以自动完成且幂等，不得靠清空 IndexedDB“解决”问题。迁移失败时不能破坏旧数据，应显示可诊断错误和导出/恢复途径。
4. 新字段合理设置默认值：老日程默认前景 normal；旧任务不应突然变为重复或有子任务。
5. 保留稳定 ID、revision、createdAt/updatedAt、tombstones 和关联完整性，为 Phase 3 GitHub 同步留条件。
6. 完整 JSON 导入导出要覆盖新模型（重复规则、例外、显示层级、标签、子任务、设置）；导入时校验引用与版本，保留导入前备份及事务回滚。
7. 所有操作离线可用。禁止把 PAT、隐私数据写入前端源码；本阶段无需任何 GitHub 认证。
8. UI 中用户提供的标题/描述必须安全渲染，避免 XSS；不要为事件标题使用不可信的原始 HTML。

## 8. 验收与自动化测试（务必实际执行）

请保留并重新运行 Phase 1 的全部测试，新增测试至少覆盖：

### 右侧拖拽

- 在真实浏览器中，从**右侧待办面板**拖动任务到周视图与日视图，操作真实成功。
- 拖动同一任务两次：数据库仍只有一个 Task、两个独立且正确引用的 ScheduleBlock。

- 08:00—23:00 长块和 08:30—09:45 短块重叠：不遮挡、标题不逐字断行，所有事件仍可打开。

- 每周指定星期的课程正确展开；仅本次取消/改时不影响其他周，整个系列修改生效。

- 使用 Phase 1 格式/数据库样本模拟升级，迁移后原任务、清单、时间块和设置完整保留。

- 子任务、标签、筛选、撤销（如完成）均有相应测试。

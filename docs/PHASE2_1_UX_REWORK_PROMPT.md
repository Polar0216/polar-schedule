# Polar Schedule — Phase 2.1：日程与任务交互重构

> 可直接交给 Codex 执行。基于已完成的 Phase 2 v0.2.0，不启动 Phase 3。目标是让日程表**简单、清晰、可直接操作**，而不仅是堆功能。

## 一、先阅读与检查

请完整阅读 `docs/PRODUCT_SPEC.md`、`docs/PHASE2_PROMPT.md`、`docs/PHASE2_REPORT.md`，检查 Phase 2 完整源码、当前 Git 状态、领域模型、Dexie schema、FullCalendar 交互和已有测试。

用户已在实际浏览器中复测 Phase 2，并反馈以下问题。这些实测反馈优先级高于此前“自动化测试通过”的笼统结论。

1. 任务清单中的任务被安排到日历后，点击日历块不能方便地编辑**这一次的安排**；“新建日程”和“新建待办”的入口、表单、操作表现得像两套割裂系统。
2. 同一 Task 安排两个时间段时，只有共享的父任务完成状态，不能分别勾选两次执行。对于分次完成和习惯打卡很不方便。
3. 重叠时仍会出现短时间块被大块盖住、只露出一条窄边的情况；深色和浅色均可能发生。小事件难看清、难点击。尤其注意普通块与背景块的混合场景。
4. 界面控件和表单太密，主操作流程不直观；多层滚动条、冗长详情、过多分散入口破坏可读性。
5. 开始/结束时间目前主要依赖原生 `datetime-local` 数字编辑，样式不统一且难操作。用户希望点击后弹出**风格统一的迷你日历**选择日期，并能直观选择小时和分钟。

**本阶段优先修复体验问题，不要增加统计、GitHub 同步、认证、推送通知、团队功能等范围外功能。**

## 二、P0：统一用户操作流程，保留正确的数据分层

不要简单将 `Task`、`ScheduleBlock`、独立 `Event` 合并为同一张表。它们的语义不同，但应当通过**同一套交互**编辑。

### 1. 点击任务关联的日历块

点击任务时间块时，打开统一的“安排详情 / 快速编辑”界面（紧凑弹层、侧边详情或响应式抽屉皆可，按现有架构实现）。最前面的区域必须让用户清楚看到并操作：

- 任务标题（可直接进入任务编辑）与所属清单；
- **本次开始和结束时间**（可在此直接修改，不必绕回其他入口）；
- **本次完成 / 撤销完成**；
- 更改本次时间块、删除本次安排；
- “查看完整任务”与“修改任务属性”入口；
- 如果同一任务已有多个安排，提示本次是第几段，并允许从任务详情查看全部安排。

独立日程点开仍可编辑日程本身；重复独立日程保留“仅本次 / 整个系列”既有语义。

禁止点击任务关联块时仅打开任务主表单，却没有直接编辑当前时间块的能力。

### 2. 统一创建入口的体验

- 日历空白处创建时，清楚提供“新建日程”与“安排已有任务”两种路径，避免创建重复任务。
- 用户从待办拖入日历后，应可立即点击新时间块进行本次编辑。
- 右侧待办卡片继续支持拖入日历，不改变 Task ID；原列表仍保留同一 Task。
- 用户需要区分：**任务**（一件要完成的事）、**安排**（执行它的某个时间段）、**独立日程**（课程、会议等不一定需要勾选完成的事件）。UI 可以统一，底层概念要清楚。
- 不增加不必要的确认步骤；编辑操作采用明确的保存反馈，不误导用户。

## 三、P0：每次安排独立完成状态

现有 Task 的 `status` 只适合表达“整个任务”的状态，不适合表达“这次 08:00—09:00 已执行、另一次还没做”。

### 数据与业务规则

- 给 `type=task` 的每个持久化 ScheduleBlock 增加**独立执行状态**，建议为 `pending/completed` 与 `completedAt`（具体结构由你结合现有 schema 设计）。
- 同一 Task 关联的多个 ScheduleBlock 完成状态彼此独立；勾选一段不影响其他段。
- **本次完成不自动将父任务标为已完成**；父任务 `status` 仍可独立修改。这是为了避免“完成一次背单词就结束整个长期任务”。
- 反过来，手动把父任务标为完成，**不能静默覆写历史安排的每次完成记录**。
- 任务详情明确显示“已完成安排数 / 总安排数”（例如 1/2），每段可单独勾选；日历块上以清楚但不抢占文字的小勾选标记表现本次完成，并能从详情撤销。
- 未安排时间的 Task 仍可通过原父任务状态管理；独立 event 不强行增加任务完成状态。
- 删除、撤销、导入/导出、日期拖动、修改时长、跨标签页、离线和以后同步预留都要维护此状态。
- 如果父任务已完成但还有未完成的安排，UI 必须避免用模糊的单个复选框误导用户：明确标示“整个任务”和“本次安排”是两件事。

**习惯相关的阶段边界**：本阶段至少实现同一任务多个已安排时间块的独立勾选，真正好用的分次打卡必须可用。无需在本阶段重写现有重复规则引擎以支持无限重复任务；如能低风险复用，可另行说明方案，但不可因此拖延 P0 修复。将“任务安排周期性自动生成与逐次打卡”列入下一小阶段建议，而不是误称已经完整支持习惯追踪。

## 四、P0：任何重叠安排都不能被彻底遮盖

请用用户场景复现并修复，而不是仅检查 `slotEventOverlap=false` 这个配置是否存在。

### 必须覆盖

- 同一天一个长块 08:00—23:00，短块 08:30—09:45（两者同为普通块）；
- 同一天长块为**背景**、短块为普通块；
- 同一天短块为**背景**、长块为普通块（用户当前遇到“短块被完全遮住”的重点）；
- 同时有三条或更多重叠块；
- 日视图与周视图、浅色与深色、窄屏。

### 交互与显示要求

- 默认普通事件并列布局，必要时保证每个事件有可识别的标记和可到达的编辑入口。
- 对于背景块，其语义是标示背景时间范围，**不能让唯一的标题、标记和交互入口全部被前景完全遮住**。可以通过背景专属顶部/侧边标识、可展开的重叠项目清单、或在该时间范围固定可见的标签实现。
- 背景不可原生拖动不是问题，但必须可以在用户能发现的入口中编辑；禁止仅依赖鼠标 hover，手机也要可达。
- 背景图层不得截获前景事件的点击/拖拽；前景事件不得让另一安排在逻辑上消失。
- 周视图列宽不足、事件数过多时，不要硬挤成几像素宽或让中文逐字换行：采用可发现的 `+N 项`/重叠选择面板，并保证能查看每项的完整时间、标题和编辑入口。
- 不得为了“解决遮盖”修改真实日程时间或静默禁止时间冲突。
- 对普通块，除截图外还要做真实浏览器几何/点击测试，确认它们确实可以被触达。

## 五、P0：一致的弹出式日期与时间选择器

替换目前观感割裂的原生日期时间数字编辑主路径；不必完全删除键盘输入途径。

设计为：点击“开始时间”或“结束时间” → 弹出统一风格的日期时间选择器：

- 左侧/上方：迷你月历，支持切换月份、年份并选择日期，高亮今天和已选日；
- 右侧/下方：24 小时制时间选择，小时与分钟可直观选择，推荐 5 或 15 分钟步长，仍可精确键盘输入；
- 明确区分开始和结束，支持跨日事件；
- 全天事件只选择日期，不出现多余的时分；
- 显示并遵守现有浏览器/IANA 时区逻辑，保留并验证 DST 异常时刻、日期往返、跨月跨年。

技术建议：优先采用成熟、可访问的日历/弹层组件（如 React DayPicker + Radix Popover 或等价开源库）并沿用现有 CSS 变量；**不要未经评估自行写一大套日期控件算法**，也不要直接引入与现有视觉语言冲突的完整 UI 框架。

要求：

- 与网站紫色强调色、圆角、浅色/深色模式一致；
- 适配桌面与手机，手机不会溢出屏幕或被软键盘遮挡；
- 键盘可访问，有清晰焦点态，支持 Esc 关闭和明确确认；
- 不允许结束时间早于或等于开始时间（既有跨日/全天特殊规则保持一致）；
- 此组件需复用在独立日程、重复日程单次例外及任务安排编辑等位置，避免出现两套样式。

## 六、P1：减少操作复杂度与视觉噪音

本阶段重点优化现有界面，不需要大改技术栈或重新实现整个日历。

- 主界面以「时间表 + 右侧精简待办」为核心；主操作尽可能一步可达。
- 任务详情优先显示标题、完成状态、本次安排、截止日期；标签、优先级、子任务、描述等可以按需展开或组织为清晰分组，不要一次性塞满竖向长表单。
- 明确显示且区分“任务截止日期”和“本次执行时间”。
- 任务块、独立日程、背景安排应有一致但可区分的视觉符号，不能完全依赖颜色。
- 优化截图中的多层滚动条：排查 FullCalendar 外层容器、日历全天区及侧边栏的固定高度/overflow，减少同一视觉区域出现多条滚动条的情况，不损失正常纵向滚动能力。
- 简化重复出现的按钮与入口；保留高级功能但通过折叠/二级区呈现。
- 右侧列表在窄屏合理收起或切换，不牺牲时间轴可读性；交互不应依赖 hover。
- 不为追求简洁而删掉 Phase 2 已交付的子任务、标签、重复规则、背景管理和撤销功能。

## 七、升级、数据保护与 Git 工作流

本项目已有用户真实本地数据，**绝不能使用清空数据库、重新初始化、覆盖旧存储作为解决方案**。

- 先备份现有状态并阅读 v2 schema。若增加每次安排的状态，需要正式 Dexie v2 → v3 升级及 JSON schemaVersion 2 → 3（具体版本要先核对当前真实代码），为旧任务时间块设定 `pending` 默认值，保留 ID、列表、任务、日程、系列和例外。
- 导入 v1/v2 JSON 时走冻结旧 schema 校验与迁移；导出采用最新模型；导入失败整体回滚；导入前快照机制保留。
- 维护 `revision`、时间戳、墓碑、撤销语义与未来 Phase 3 同步扩展所需的稳定 ID。
- 不得改变 `Task` 与时间块的多对一引用关系。
- 更新现有规格补充与 README，不改写原始需求历史。
- 从当前完整 Phase 2 分支的代码继续，独立创建 `feature/phase2-1-ux-rework` 或等价安全分支；先检查未提交修改。不 push、merge、rebase、reset、clean、force push，不擅自修改其他仓库。
- 不使用 PAT、不访问 GitHub 私有数据仓库，不提前开发 Phase 3。

## 八、必须执行的测试与验收场景

除原 Phase 1/2 回归测试外，新增以下真实浏览器 E2E，不能只做静态快照：

1. 建立 Task A，分别安排周一 08:00—09:00 与周二 09:00—10:00；点击**日历中的第一块**，修改其时间；检查第二块不变且 Task A 仍只有一个。
2. 点击第一块“本次完成”，检查第一块显示完成、第二块待完成、父 Task 仍未完成；再将第二块完成，分别撤销一次；刷新、关闭重开与导出导入后状态一致。
3. 在列表将父 Task 标记完成，不得把未完成安排自动全部改为完成；父子两个层级状态在 UI 上仍可区分。
4. 分别测试普通/普通、背景/普通（两种主次互换）、三重以上重叠；短块不能只剩无法点击的窄条，隐藏或折叠的块在可见列表可编辑。
5. 真鼠标测试前景事件点击、拖拽、拉伸，确保背景层不抢事件；任务列表仍可拖入周/日视图。
6. 迷你日历选择跨月日期，时间选择精确到分钟；浅/深主题截图；手机宽度与键盘交互；非法结束时间得到校验反馈。
7. 使用隔离浏览器运行 v2 → 新版本数据库迁移，旧任务/安排/标签/重复课程/主题和备份保持，默认安排状态符合预期；v1/v2 JSON 升级与导出/恢复回归。
8. 完整执行 typecheck、unit/component tests、production build 和全部 E2E。不能删除、禁用或篡改旧测试来掩盖失败。

**重要**：对之前“原浏览器拖拽未复现”的情况继续诚实记录，不可声称已有确证根因。本阶段结束时建议用户在相同浏览器、同一生产预览地址再验证。

## 3. GitHub API 通路与错误处理

目标使用 GitHub Contents API：

- GET `/repos/{owner}/{repo}` 检查目标仓库真实存在、可访问、`private` 属性、默认分支，拒绝意外连公开仓库；不要用 PAT 对任意用户自定义 URL 发送 Authorization。只允许 GitHub 固定可信 API origin，严格校验 owner/repo/path。
- GET `/repos/{owner}/{repo}/contents/data/polar-schedule.json?ref=main` 读取远端快照/当前 blob SHA。初次不存在文件是可解释的 404；仓库不可访问或权限不足不是“空仓库”，不得盲目初始化或覆盖。
- PUT 相同 contents 路径，Base64 UTF-8 JSON，更新必须携带读取到的 `sha`，创建时不带；指定明确 commit message 和 `branch`。
- 注意官方文档指出该 API 的写入/删除并发可能冲突；对同一目标串行写入，不可以一连串无条件覆盖，遇到 409/422 重新检查远端并进行合并，而不是简单强行覆盖。
- 支持 401、403、404、409、422、429、5xx、网络中断、token 过期/被撤销、速率限制/`Retry-After`、未知提交结果。读取 `x-ratelimit-*`，退避重试有上限；不要高频轮询或形成提交风暴。
- 真实测试的首次初始化必须严格绑定 `Polar0216/polar-schedule-data-test`，只能向其中写入初始化文件及独立的测试数据路径，如 `data/phase3-e2e/<run-id>.json`；普通的 `data/polar-schedule.json` 用于应用逻辑，不得自动用测试覆盖已有真实数据。对测试路径产生的文件可以在完成验证后按明确归属清理，但**禁止删除仓库、改仓库可见性、批量清空或覆盖非本次创建文件**。若缺少权限、发现仓库非私有、owner 不符或远端已有不可识别内容，立即停止真实写入，仅保留 Mock 测试。
- 用户已授权在隔离测试环境进行真实 GitHub API 操作，成功后应在报告中明确标识真实测试与 Mock 测试各自的通过/失败范围；不能把少量真实测试描述成多设备冲突全量实网验收。
- 单个远端 JSON 建议控制在约 1 MB 以下的可可靠 Contents API 范围；超出应阻止写入、允许独立导出、展示安全迁移/分片建议，绝不截断数据或静默丢记录。不要没有测试就引入复杂 Git Trees API 方案。
- JSON 必须稳定排序/序列化，避免相同内容生成无意义新提交；相同状态不得重复上传。

## 4. 远端数据格式、兼容与安全边界

- 使用清晰的文件头 / 协议版本（例如 `format: polar-schedule-snapshot`、`formatVersion:1`）包裹现有领域 `schemaVersion:3` 快照；不要因为引入云端包装就破坏用户已有 v1/v2/v3 JSON 导入导出协议。
- **必须包含**可同步的实体：lists、tasks、scheduleBlocks、tags、重复系列、例外、tombstones，以及跨设备应共享的领域设置。完整保留任务独立完成状态与 completedAt、ID/revision、UTC 时间、IANA 信息和关联约束。
- **不得同步** PAT、密钥、解锁密码、浏览器缓存、IndexedDB 内部数据库备份、设备本地撤销栈、DevTools/日志、服务工作线程元数据。设备特定 UI 状态（例如某个侧栏是否折叠）优先保持本机，不要让另一设备不断覆盖；如设置同时含共享/本机字段，明确拆分并测试。
- 使用冻结的旧校验器/现有迁移管线，下载后先严格验证 JSON 及引用关系，再考虑合并；不允许为了兼容而放宽 schema 或自动补造不存在的关联。
- 远端 JSON 仅用于数据内容，不允许在反序列化时执行任何代码。文本继续使用 React 安全文本渲染。
- 将仓库 branch/path/环境标识记录为本地配置，并与 sync base 绑定；切换测试/正式仓库时不能复用上一个仓库的 SHA、base、冲突结果或凭据。

## 5. 本地优先、队列与真正安全的三方合并

请不要用简单的“谁更新时间更新谁覆盖谁”作为冲突处理。

### 5.1 三方输入与持久状态

每个仓库环境独立维护：
- `base`：该设备上次已确认同步成功的完整共同祖先快照；需要持久化，以便关闭网页或脱机后恢复比较。
- `local`：此设备当前事务一致的 IndexedDB 领域状态。
- `remote`：刚刚从 GitHub 获取且严格校验的当前状态与 blob SHA。

在同步时计算 `merge(base,local,remote)`；最后提交后才更新 `lastSyncedBase`、远端 SHA 与同步成功时间。如果上传请求结果不确定，先向远端核实最新 SHA/内容再决定是否重试，避免重复/丢数据。

### 5.2 实体合并语义

- 以稳定 ID 合并 lists、tasks、scheduleBlocks、tags、重复系列、例外、删除墓碑等；不同设备修改不同记录时自动合并；同一记录两边做了完全一致的更改可以视为无冲突。
- 同一 ID 两边都做了不同更改，或一侧删除另一侧修改：判定为**冲突**，不得自动用 updatedAt、revision 或客户端时钟选胜者。支持清晰的用户选择：保留本地 / 保留云端；必要时先导出两边数据再确认。复杂冲突不用一期做精细字段级合并，但绝对不能吞掉任意一方。
- 新创建记录的 ID 冲突、同时修改关联实体、墓碑与重新创建、重复系列及例外引用、标签/清单删除对任务的影响，都要验证。合并后的快照必须通过 schema + 跨表引用验证，否则暂停同步、保留本地/远端原状态。
- 本地修改尚未提交之前，远端改变时必须先拉取/合并，再尝试 PUT；PUT 409 时重新获取 remote 再合并/重试（有限次数）。
- 页面刷新、关闭重开、离线变在线、两标签页同时编辑都不能失去尚未同步的写入，也不能把排队状态误显示为已同步。
- 将本地的并发同步锁与当前版本事务协调，避免自己同一浏览器多标签反复写入同一个文件；跨设备仍以 GitHub 远端冲突机制为最终边界。

### 5.3 频率与触发

- 本地编辑立即写 IndexedDB，并标记“待同步”；**绝不等待 GitHub 成功才允许编辑**。
- 自动同步采取防抖和合并批次（例如修改后数秒、窗口恢复/重新联网时检查），在合理节流下工作；支持“立即同步”。一次本地连续多次改动尽量合并一次 commit。
- 不写无限轮询，不为每次勾选生成单独 GitHub commit。
- 失败时记录可理解原因、下次重试条件和待同步数量，显示真实同步状态。
- 支持撤销令牌、主动断开和临时离线：**断开同步不删除日程**。

## 6. 首次连接和设备启动必须安全

这是高优先级验收项：

1. `local` 和远端都空：展示初始化预览，用户确认创建远端文件。
2. 本地已有数据、远端无快照：**不自动上传**，提示数据摘要/目标私有仓库，明确让用户确认“以本地创建测试仓库数据”。
3. 本地为空、远端有快照：**不自动清库/覆写**，提示从远端导入，提供确认和备份（包括空状态说明）。
4. 双方已有数据、没有可信共同 base：不得假装可以比较修改；引导选择保留本地/保留远端/导出后处理，或做明确且无歧义的首次实体合并预览，冲突必须展示。
5. 已有同步基础的普通重连：按三方合并，未同步本地数据不能被直接覆盖。
6. 连接目标不是私有仓库、不是选定测试仓库、权限不足、文件格式损坏：明确报错，不做危险后续写入。
7. 测试环境和正式环境必须显著区分，例如状态栏“测试仓库”；Phase 3 UI 可预留正式模式但**实际开发期间不自动写入正式仓库**。切换目标前提示数据归属、base 隔离及风险。

## 7. 登录/记住设备/密钥管理

用户明确不想每次打开网页都输入 PAT，但愿意承担非敏感待办项目的合理风险。要诚实区分两种模式：

### A. 可信设备便捷模式（主要体验需求）

- 首次用户主动粘贴 fine-grained PAT，点击“记住此设备”后持久保存于此浏览器来源的**本地凭据存储**（优先封装 IndexedDB）；刷新/关闭重开不再要求重复输入，未失效即可自动连接。
- 必须显示安全说明：纯静态前端若要自动请求私有 GitHub API，浏览器必须保留可用凭据；浏览器存储、扩展、XSS 或本机受控可能造成令牌泄露。“记住此设备”不等于服务器端安全登录，也不等于端到端加密。
- 不应宣称“将 PAT 与同源可直接使用的设备密钥一起存储就彻底安全”；如果采用设备密钥仅提升特定静态数据窃取门槛，需要诚实说明恶意页面脚本仍能借助同源能力使用令牌。
- 提供“断开并清除本设备凭据”按钮、重新授权及令牌到期说明；清凭据与删数据分开。

### B. 口令加密模式（可选的更安全模式）

- 使用 Web Crypto API、每条密文独立 salt/nonce，PBKDF2 派生口令密钥 + AES-GCM 认证加密；浏览器只持久化密文及必要 KDF 元数据，解锁口令不落盘，关闭会话后再次解锁。不得自写密码学算法或在源码硬编码密钥。
- 允许从便捷模式切换为口令模式、反向切换前明确风险，验证修改口令/错误口令/清凭据等场景。若实现成本明显威胁同步正确性，可先完整交付安全边界清晰的可信设备模式，并将口令模式标记为**未完成**、单独列后续任务，绝不能用虚假的“加密保存”替代。

安全基础：
- 永远不把 PAT 注入 React 普通展示状态、URL query、history、通知、日志、错误上报、下载文件、local export、CI、截图、README 示例、编译期 `VITE_*` 配置。
- 授权 header 只发给固定 `https://api.github.com`；不允许任意 GitHub Enterprise host 或不受信任的重定向把 Authorization 带走。默认拒绝非 GitHub API 的远程请求。
- 保持 CSP/HTML 转义安全，不引入不必要第三方运行脚本，避免 `dangerouslySetInnerHTML`；生产静态构建不得包含秘密。
- 令牌用**单仓库 fine-grained PAT**，过期需手动生成新令牌，不承诺永久免授权。不能擅自让用户授权整个账户、经典 `repo` 广泛权限或写 GitHub Workflows。

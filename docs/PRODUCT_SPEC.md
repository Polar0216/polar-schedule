> 版本：v0.1（开发基线）  
> 日期：2026-10-19  
> 状态：待开发  
> 目标读者：项目维护者、Codex/其他开发代理

## 0. 项目定位与约束

**Polar Schedule** 是一款面向单人使用的免费、开源、可自托管的个人日程与任务规划 Web 应用。它同时提供：

1. **带明确时间段的日程表**：周 / 日时间轴及月历，直观看到「什么时间做什么」。
2. **高度可定制的清单**：按课程、项目、生活等自由创建、排序、筛选、归档清单。
3. **任务与日历联动**：任务可以先进入清单，随后安排到时间轴；完成状态、截止日期与时间安排互不混淆。
4. **离线优先、跨设备同步**：本地可用，使用 GitHub **私有仓库**存储和同步非敏感日程数据。
5. **低运维成本**：公开前端通过 GitHub Pages 部署，**不使用自建服务器，也不要求付费服务**。

这是个人工具，不是团队协作平台。第一版**不做**多人账户、共享日历、即时通信、团队权限管理、复杂项目依赖、付费功能或外部日历双向同步。

**非目标与安全边界：**

- 日程数据以一般个人安排为主，不建议存储密码、身份证件、API 密钥等敏感信息。
- GitHub Pages 是公开的：前端源码、打包后的 JavaScript、静态资源均视为公开。**私有数据和 PAT 绝不能打包进前端。**
- 纯静态网站直接访问 GitHub 私有仓库，需要浏览器在运行时取得授权；**无法仅靠浏览器本地加密同时实现完全无感登录和防范同源恶意脚本**。设计应如实向用户说明取舍。

## 1. 用户场景与关键体验

### 1.1 主要场景

- 查看本周课程、健身、会议、学习和开发计划，快速发现时间冲突与空闲时段。
- 将「完成实验报告」记在「课程学习」清单，设定周五截止，但暂不安排时间；之后拖到周三 19:00–21:00。
- 把「每周五的固定安排」设成重复日程，而不是每周手动重建。
- 按清单、颜色、优先级和完成情况筛选当前视图。
- 手机临时新增待办；离线也能写入，联网后再同步到 GitHub。
- 在电脑、手机、平板之间同步；同步状态必须清楚、不能无提示覆盖数据。

### 1.2 产品设计原则

- **时间优先**：默认「周视图」，主要视觉空间给时间轴。
- **待办与时间分离**：任务可以没有时间，时间安排不自动等于任务完成。
- **同一任务、多个工作时段**：一个任务可以安排到多个时段，例如周二准备、周四收尾。
- **可定制而不复杂**：清单、颜色、可见性、视图密度、时间粒度由用户配置；默认界面保持简洁。
- **数据归用户所有**：可导出 JSON，私有仓库存有版本记录，具备恢复手段。
- **先可靠，再好看**：离线保存、同步和冲突处理优先于动画或高级统计。

- 优先展示**单日时间轴 / 简化周视图 / 待办列表**，避免直接压缩桌面七列时间轴。
- 清单作为抽屉或底部导航入口，详情使用弹层。
- 除拖拽外，必须始终有「选择日期与起止时间」的表单操作，确保触屏、小屏和辅助技术可用。
- 适配 PWA 安装、窄屏滚动；离线功能不能依赖 PWA 安装。

## 3. 核心概念与行为约定

> 必须先理清以下三个实体，避免在开发中把「清单任务」和「日程事件」混成一种记录。

### 3.1 清单（List）

用于管理一组任务，例如「课程学习」「个人项目」「生活运动」。

- 创建、重命名、删除/归档、改颜色、改图标、手动排序。
- 支持按清单筛选任务和日历的可见内容。
- 预置「收集箱」，用户可新增任意数量清单。
- 删除清单前必须确认：默认建议将任务移至收集箱；不要静默连带删除所有任务。
- **第一版不做多层嵌套清单**；后续可扩展清单分组。

### 3.2 任务（Task）

表示「需要完成的事情」，本身可以**没有开始时间**。

- 字段：标题、所属清单、描述、状态、优先级、截止日期、排序、子任务（Phase 2）、标签（Phase 2）。
- 状态：`todo` / `in_progress` / `done`；完成可保留完成时间，并支持撤销。
- 截止日期 `dueDate` 与执行时间 `ScheduleBlock` 是不同概念。
- 同一任务可对应 **0 到多个**时间块，避免长任务只能安排一次。
- 完成某个时间块**不等于**任务完成；任务的完成由用户明确设置。

### 3.3 时间块（ScheduleBlock）

表示「某一段时间的安排」，有两种类型：

1. **独立日程事件 `event`**：课程、会议、固定活动等；不必属于待办清单。
2. **任务安排 `task`**：引用已有任务 ID，表示为这个任务预留的时间；不复制任务内容。

共同支持：起止时间、颜色/分类、全天标记、备注（独立事件）、重复规则（Phase 2）。

**重要交互：**

- 将任务从清单拖入时间轴 → 创建一个关联该任务的时间块，不复制任务。
- 再次拖入同一任务 → 创建第二个时间块，仍引用同一个任务。
- 移动或调整时间块 → 只改变时间安排，不修改任务截止日期。
- 删除一个任务安排时间块 → 默认只删除这段安排，**不删除任务本身**。
- 删除任务时若存在关联时间块 → 必须确认如何处理，默认移除关联时间块。
- 时间块重叠允许存在，但以可视化重叠提示；不自动禁止课程或事项并行。

### 3.4 示例流程

1. 在「课程学习」新增任务「完成杨氏模量实验报告」，截止周五。
2. 左侧清单与右侧未安排任务面板可看到该任务；由于还没安排时间，周视图不显示执行时间块。
3. 将任务拖到周三 19:00，调整到 21:00，创建关联时间块。
4. 如需补充时间，再安排周四 20:00–21:00，任务仍只有一条。
5. 点击任务完成，清单显示完成状态；其时间块可以保留为历史记录。

## 4. 功能优先级

### 4.1 Phase 1：可使用的本地 MVP（P0）

- 日、周、月三种日历视图；默认周视图，日历导航与“回到今天”。
- 纵向时间轴；点击空白处创建日程，编辑标题、日期、起止时间；拖拽移动与拉伸时长。
- 新建、编辑、删除、归档清单；可配置颜色；调整清单排序。
- 新建/编辑/完成/删除任务；设置所属清单、截止日期、优先级。
- 从任务清单向时间轴创建关联时间块；也可通过表单安排时间。
- 清单显隐、未安排任务筛选、完成状态筛选。
- 本地 IndexedDB 持久化；刷新或关闭浏览器后数据不丢失。
- 响应式布局、基础浅色/深色模式。
- 本地 JSON 导出与导入，含格式校验和导入前备份提示。
- 单元测试覆盖核心数据关联、增删改和日期转换。

**阶段验收：**断网时也能独立新增任务/安排时间；重启浏览器数据保留；任务拖到日历不会复制或自动完成。

### 4.2 Phase 2：进阶规划能力（P1）

- 重复事件（日 / 周 / 月、间隔、结束条件），支持「仅编辑本次 / 编辑整个系列」。
- 任务子任务、标签、备注，任务排序及简易搜索。
- 时间段粒度 15/30/60 分钟、默认起止显示时段、周起始日、默认视图等设置。
- 颜色、图标、显示字段、清单筛选设置持久化。
- 常用快捷操作：复制日程、跳转指定日期、撤销误操作（至少提供删除确认/短时撤销）。
- 时区与夏令时边界测试；周期任务的重复模型单独评估后实现，不与事件重复混为一谈。

**阶段验收：**重复日程跨周显示正确；编辑单次不误改整组；调整时间粒度与起始日后设置可以保存。

### 4.3 Phase 3：GitHub 私有仓库同步与授权（P0，正式发布必需）

- 首次配置：填写私有数据仓库的 Owner / Repo / 默认分支，以及 fine-grained PAT。
- 验证访问权限及是否有 `Contents: Read and write` 权限（通过实际读写流程与友好错误提示确认）。
- **不要求每次输入 PAT**：支持加密保存令牌，打开网站后使用解锁口令解密；可选「信任此设备」免重复解锁，明确告知其安全代价。
- 自动同步：本地先保存，联网后防抖批量上传；支持手动“立即同步”。
- 明确显示状态：未配置 / 本地已保存 / 待同步 / 正在同步 / 已同步 / 同步冲突 / 授权过期 / 离线。
- 读取远端并合并；检测 GitHub 文件 SHA 冲突，不可静默覆盖其他设备更改。
- 可重新配置 PAT、退出/清除此设备凭据，且**清除凭据不等于删除本地任务**。
- 错误可恢复：断网、GitHub 限流、超时、403、404、409 等有明确提示和重试策略。

**阶段验收：**电脑 A 新增日程并完成同步，电脑 B 首次配置后可拉取；两端离线修改同一任务后恢复联网，不发生静默数据丢失。

### 4.4 Phase 4：体验、备份与发布（P1）

- PWA 图标、Manifest、基础离线静态资源缓存；更新后能够刷新获取新版。
- 手机和平板适配、键盘操作、可访问性、空状态与错误页。
- GitHub Pages 自动部署，公开仓库中提供 README、截图、部署指引与 LICENSE。
- 同步操作记录、导出备份、GitHub 历史版本恢复操作说明。
- 移除开发测试数据需独立确认；不得自动删除真实数据仓库。

**阶段验收：**PC 与移动端可用；全新用户能按 README 部署；用户能导出数据并根据说明恢复一次备份。

## 5. UI/UX 具体要求

### 5.1 日历

- 默认一周七天，展示全天区域与按小时展开的纵向时间轴。
- 时间轴支持跨天导航、滚动、当前时间线、今日高亮、重叠事件排布。
- 时间显示遵循浏览器/用户设置时区，使用 24 小时制（以后可扩展）。
- 月视图侧重概要，不要求与周视图相同的可视化密度。
- 支持拖拽与拉伸，但关键流程必须可通过点击/表单完成。
- 新建时间块起止时间合理校验：结束时间必须晚于开始时间（跨日事件另行明确标示）。
- 对全天、跨日、重复事件分别测试；不要混用仅日期值和 UTC 时间戳。

### 5.2 清单与任务

- 清单可设置自定义名称、颜色、图标、顺序、显隐、归档。
- 收集箱作为无明确归类任务的默认容器。
- 可以只做清单、不安排时间；也可以只建独立日程事件、不建任务。
- 点击清单展示其任务；提供未安排、即将截止、已完成等快速视图。
- 同一任务在清单、详情与时间轴上展示的信息必须一致。

### 5.3 外观与设置

- 视觉方向：干净、克制、统一；浅色与深色模式；避免重度仪表盘堆砌。
- 桌面支持折叠侧栏与详情栏。
- 设置中心：默认视图、周起始日、时间颗粒度、工作日与显示时段、主题、清单可见性、GitHub 同步设置、数据导入导出。
- 通知不是第一版硬要求；浏览器关闭后不能承诺一定触发提醒。

## 7. 领域数据模型（第一版契约草案）

原则：**ID 稳定、类型明确、时间准确、支持迁移。** 示例供实现时调整，但不能破坏「Task 与 ScheduleBlock 通过 ID 关联」的核心设计。

```ts
type UUID = string;
type ISODate = string;      // 例如 2026-10-23：仅日期，不带时区
type ISOInstant = string;   // UTC ISO 8601，例如 2026-10-21T11:00:00.000Z

type TaskStatus = 'todo' | 'in_progress' | 'done';
type TaskPriority = 'none' | 'low' | 'medium' | 'high';

interface List {
  id: UUID;
  title: string;
  color: string;
  icon?: string;
  order: number;
  archived: boolean;
  createdAt: ISOInstant;
  updatedAt: ISOInstant;
}

interface Task {
  id: UUID;
  listId: UUID;
  title: string;
  description?: string;
  status: TaskStatus;
  priority: TaskPriority;
  dueDate?: ISODate;           // 截止日期，不等于安排的时段
  completedAt?: ISOInstant;
  order: number;
  createdAt: ISOInstant;
  updatedAt: ISOInstant;
}

interface ScheduleBlock {
  id: UUID;
  type: 'event' | 'task';
  taskId?: UUID;               // type='task' 时必须有且有效
  title?: string;              // 独立 event 必填；task 默认读取任务标题
  description?: string;
  startAt: ISOInstant;
  endAt: ISOInstant;
  timeZone: string;            // IANA 时区，如 Asia/Shanghai
  allDay: boolean;
  color?: string;
  recurrence?: {
    rule: string;              // Phase 2：规范化的 RRULE 或等价定义
    seriesId?: UUID;
  };
  createdAt: ISOInstant;
  updatedAt: ISOInstant;
}

interface ScheduleSettings {
  defaultView: 'day' | 'week' | 'month';
  weekStartsOn: 0 | 1;         // 周日或周一
  slotMinutes: 15 | 30 | 60;
  startHour: number;
  endHour: number;
  timeZone: string;            // 默认来自浏览器，可手动覆盖
  theme: 'system' | 'light' | 'dark';
  hiddenListIds: UUID[];
}

interface Tombstone {
  entityType: 'list' | 'task' | 'scheduleBlock';
  id: UUID;
  deletedAt: ISOInstant;
}

interface ScheduleDataV1 {
  schemaVersion: 1;
  lists: List[];
  tasks: Task[];
  scheduleBlocks: ScheduleBlock[];
  settings: ScheduleSettings;
  tombstones: Tombstone[];
  updatedAt: ISOInstant;
}
```

实现注意：

- ID 由 `crypto.randomUUID()` 等可靠方法生成；不能使用数组下标充当 ID。
- 普通单次时间块内部存 UTC instant，界面按 IANA 时区转换。全天事项另行设计成日期范围（而非使用 UTC 零点猜测）；上述接口是草案，**正式实现时应把全天日期字段显式建模**。
- **重复日程**要保存“本地墙上时间 + 时区 + 重复规则 + 排除/覆盖记录”，避免夏令时导致每周固定活动漂移；在 Phase 2 完整细化后启用。
- 删除必须保留墓碑或等价变更日志，避免离线设备重新上传已经删除的旧记录。
- 设置若跨设备同步，应进入数据文档；设备相关的「凭据」「本地 UI 缓存」不得写入远端。
- 所有持久化数据均进行运行时 schema 校验和版本迁移；不得直接信任 GitHub 返回的 JSON。

## 8. GitHub 存储与同步设计

### 8.1 仓库约定

```text
polar-schedule            公开仓库：网页源码和 GitHub Pages
polar-schedule-data       私有仓库：日程及配置数据
└── data/
    └── schedule.json      首版唯一主数据文件
```

- 首版使用单个 `schedule.json` 减少跨文件非原子更新和同步复杂度。个人数据规模通常足够。
- 可以通过配置指定 Owner / Repo / Branch / File Path，不硬编码仓库归属。
- 当未来数据量明显增长，再规划分文件、分页或差量同步，不提前过度设计。
- `schedule.json` 不含 PAT、解锁口令、浏览器设备密钥。

### 8.2 本地优先写入协议

1. 用户编辑任务或时间块 → 立即写 IndexedDB，同时增加本地未同步变更记录。
2. UI 立即显示修改，显示“待同步”，不阻塞用户操作。
3. 网络可用且已解锁 → 防抖聚合（例如编辑停止约 3–10 秒后）并同步；提供手动同步按钮。
4. 同步前读取当前远端文件和 GitHub 提供的 blob SHA（或等价版本标识）。
5. 在确认基线后，合并本地未同步变更与远端新变更，生成新的完整 JSON。
6. 使用 GitHub Contents API 提交文件，更新时携带读取到的 SHA；发生 409/版本冲突时重新拉取并进入冲突恢复流程。
7. 提交成功后更新本地同步基线、清除对应已确认变更；若失败，保持本地待同步数据。

### 8.3 冲突处理（必须实现，不可忽略）

- **不同实体并发修改**：按 ID 合并，例如设备 A 新增任务、设备 B 新增日程，应都保留。
- **同一实体不同字段修改**：能明确安全合并时按字段合并；无法确认则展示冲突。
- **同一字段并发修改**：显示本地值与远端值，允许用户选择，不静默以时间戳覆盖。
- **删除与编辑冲突**：不能因远端没有记录就复活本地旧记录；需要 tombstone/变更日志和明确处理。
- 同步出错不得清除本地操作队列；显示错误状态与重试入口。
- 初始化首次拉取/同步时，如远端和本地均有数据，**先提示合并/备份**，不得自动全量覆盖任一端。

### 8.4 同步性能与可靠性

- 仅在发生变更时写 GitHub，防抖聚合，避免一次点击一次 commit。
- 页面重新获得焦点、网络恢复、用户手动请求时检查远端更新。
- 尊重 GitHub API 限流；使用退避重试，不进行高频轮询。
- 浏览器页面关闭前允许存在未上传数据；UI 明确标出“本地已保存，尚未同步”。
- 提供最后成功同步时间；该时间只表示云端同步完成，不与本地保存混淆。
- 可借助 GitHub 提交历史回滚，但应先备份当前本地内容，避免误操作。

## 9. 认证、安全与“保持登录”

### 9.1 既定方案：不使用自建服务器

使用 GitHub **fine-grained PAT**，仅授权数据仓库所需的最小权限：

- Repository access：`Only select repositories`，只允许 `polar-schedule-data`。
- Repository permissions：通常仅需要 `Contents: Read and write`；若额外请求权限，必须解释用途。
- 设置到期时间；令牌过期时提供重新输入界面。
- **不同项目不共用高权限 PAT**，不要把单词网站的通用凭据直接复制到这里。

### 9.2 本地凭据保存的两种模式

**推荐默认：加密保存 + 解锁口令**

- 首次填写 PAT 和本地解锁口令。
- 使用 Web Crypto API：基于用户口令和随机盐派生密钥（PBKDF2），使用随机 IV 的 AES-GCM 加密 PAT。
- IndexedDB **只存密文、盐、算法参数和 IV**，不存明文 PAT、口令或可直接恢复的派生密钥。
- 解锁后令牌只在当前运行会话内存中使用；下次重新打开网页只输入解锁口令，**不用重新找 PAT**。
- 支持主动锁定、清除本地凭据及重新配置。

**可选：信任此设备（打开即用）**

- 用户主动选择后，可在设备本地保存能够自动恢复访问能力的凭据/密钥。
- 必须明确告知：这种“无感解锁”只提供使用便利，不提供强于同源 JavaScript 的攻击隔离；即使密钥不可导出，恶意网页脚本仍可能在当前源执行解密或发起授权请求。
- 默认关闭；公共设备或不可信浏览器不建议使用。
- 不允许把“加密存储”宣传为能够阻止 XSS 窃取会话权限。

### 9.3 前端安全要求

- 绝不在仓库源码、`.env` 打包变量、URL 查询参数、GitHub Actions 日志、错误日志中输出 PAT。
- 避免 `dangerouslySetInnerHTML` 与未经清洗的富文本；任务标题/备注按普通文本渲染。
- 减少第三方脚本及依赖，引入 Content Security Policy（在 GitHub Pages 的可行范围内通过 HTML meta/CSP 控制）。
- GitHub API 仅向预期的 HTTPS 端点发送授权头；不要让用户可控 URL 接受 Bearer Token。
- 不在 Service Worker 缓存 GitHub API 授权响应或 PAT。
- 浏览器数据清理、换设备或无痕模式可能使本地加密凭据失效；这时需要重新授权。
- 私有仓库比 Secret Gist 更合适：Secret Gist 不应当作访问权限受限的数据存储。

## 10. 导入导出、备份与恢复

- 导出所有清单、任务、时间块、设置为带 `schemaVersion` 的 JSON 文件。
- 导入前校验 schema、日期、关联 ID、重复 ID，并预览记录数；提供“合并”和“替换”两种明确的操作选项。
- 覆盖前自动尝试在本地生成备份并提示导出；不可无确认清空现有数据。
- 数据仓库 Git 提交历史可作为额外版本备份，但不等同于独立的离线备份。
- 首版至少提供恢复流程文档，不需要一开始就做复杂的可视化时间机器。

## 11. 测试与质量验收

### 11.1 业务正确性

- 起止时间校验、跨日活动、全天事件、不同浏览器时区。

### 11.4 易用性

- 1440px 桌面、768px 平板和 390px 手机宽度下可完成新增/编辑/安排任务。
- 无拖拽操作能力时也可完整使用主要功能。
- 深浅主题、键盘操作、可读颜色对比、同步状态提示可正常工作。
